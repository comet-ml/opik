Opik 2.0 organizes everything around **projects**. Data created after upgrading is automatically project-scoped. Data created on Opik 1.x — datasets, prompts, experiments, optimizations, automation rules, and alerts — requires six background jobs to assign each item to the right project. This page walks you through running those jobs.

<Warning>
  **Upgrading from Opik 1.x with existing data?** Recent Opik images ship the Opik 2.0 UI as the only experience, regardless of your existing entities. 1.x entities that have not yet been assigned to a project (no `project_id`) will not be visible in the 2.0 UI until you run the migration jobs below.
</Warning>

<Warning>
  **Run the migration on Opik 2.0.54 through 2.2.17, not on the latest release.** The six migration jobs were removed in Opik 2.2.18. Upgrade to a version in that range first, complete every step on this page, and only then [upgrade to the latest release](#upgrade-to-the-latest-release). If you upgrade straight to 2.2.18 or later, the flags below have no effect and your 1.x data stays unassigned.
</Warning>

## Before you start

1. **Take a database snapshot.** Each job writes to MySQL or ClickHouse. Back up both before starting — see [Advanced ClickHouse backup](/self-host/backup) for ClickHouse, and use `mysqldump` or your RDS snapshot tooling for MySQL. Take it before you change the Opik version.
2. **Run a supported Opik version.** Your `opik-backend` must be on **2.0.54 through 2.2.17** before you enable any flag. We recommend **2.2.17**, the last release that includes the jobs. Avoid 2.0.53 and older: their prompt migration can stall on workspaces with ambiguous prompts. See [Pin a supported version](#pin-a-supported-version) below.
3. **Confirm your deployment is healthy.** The `opik-backend` container should be running with no restart loops, and MySQL and ClickHouse should be at baseline load.

### Pin a supported version

<Tabs>
  <Tab title="Docker Compose">
    Check out the `2.2.17` tag of the Opik repository so the Compose files match the images, then start Opik on that version:

    ```bash wordWrap
    git fetch --tags && git checkout 2.2.17
    OPIK_VERSION=2.2.17 ./opik.sh
    ```

    Export `OPIK_VERSION=2.2.17` in the shell you use for the `docker compose` commands below, so the backend stays on that version when you restart it.
  </Tab>
  <Tab title="Kubernetes / Helm">
    Pin both the chart and the images to `2.2.17`:

    ```bash wordWrap
    VERSION=2.2.17
    helm repo update
    helm upgrade opik opik/opik -n opik -f values.yaml --version $VERSION \
        --set component.backend.image.tag=$VERSION \
        --set component.python-backend.image.tag=$VERSION \
        --set component.python-backend.env.PYTHON_CODE_EXECUTOR_IMAGE_TAG="$VERSION" \
        --set component.frontend.image.tag=$VERSION
    ```

    The `helm upgrade` commands in the steps below keep `--version 2.2.17` and add `--reuse-values`, so the chart and image tags stay on 2.2.17 while you toggle the flags.
  </Tab>
</Tabs>

<Note>
  Running Comet's enterprise self-hosted deployment? Its Helm chart includes an `opik.v2Migration` option that runs these jobs in the right order for you. Ask your Comet team which chart release to use.
</Note>

## How the jobs work

Each job runs inside `opik-backend` on a 30-second cycle. They are:

- **Safe to run alongside live traffic** — no user-visible locks; users can keep working throughout.
- **Resumable** — stopping a job mid-run and re-enabling it picks up where it left off.
- **Stoppable, not undoable** — already-committed writes stay; there is no rollback mode.

When an item's associated data spans multiple projects, it is assigned to the **dominant project** — the one most referenced by its runs. When no project can be determined at all (no associated runs, or the original project was deleted), it falls back to the workspace's **Default Project**, which is created on demand if missing.

## Order of execution

<Warning>
  Run the jobs in the order below. Datasets, prompts, and optimizations infer their project from
  `experiments.project_id`. Starting them before the experiment job finishes silently routes those
  items to Default Project with **no retry** — they are not re-evaluated once experiments land
  their correct project later.
</Warning>

| Step | Jobs | Dependency |
|------|------|------------|
| 1 | Experiments | None — run first |
| 2 | Datasets, Prompts | After Step 1 completes |
| 3 | Optimizations | After Steps 1 and 2 complete |
| 4 | Automation Rules, Alerts | Independent — run at any point |

## Step 1 — Experiments

### Enable

<Tabs>
  <Tab title="Docker Compose">
    Create `deployment/docker-compose/docker-compose.migration.yaml` with the flag. Pass it with its own `-f` on every command below: when you name files with `-f`, Docker Compose does not load override files automatically.

    ```yaml wordWrap
    services:
      backend:
        environment:
          - EXPERIMENT_PROJECT_MIGRATION_ENABLED=true
    ```

    Apply:

    ```bash wordWrap
    docker compose -f deployment/docker-compose/docker-compose.yaml \
      -f deployment/docker-compose/docker-compose.migration.yaml up -d backend
    ```
  </Tab>
  <Tab title="Kubernetes / Helm">
    Add to your Helm values file:

    ```yaml wordWrap
    component:
      backend:
        env:
          EXPERIMENT_PROJECT_MIGRATION_ENABLED: "true"
    ```

    Apply:

    ```bash wordWrap
    helm upgrade opik opik/opik -n opik -f values.yaml --version 2.2.17 --reuse-values
    ```
  </Tab>
</Tabs>

### Watch for completion

<Tabs>
  <Tab title="Docker Compose">
    ```bash wordWrap
    docker compose -f deployment/docker-compose/docker-compose.yaml logs -f backend \
      | grep -i "experiment.*migration"
    ```
  </Tab>
  <Tab title="Kubernetes / Helm">
    ```bash wordWrap
    kubectl logs -n opik deployment/opik-backend -f | grep -i "experiment.*migration"
    ```
  </Tab>
</Tabs>

The job is done when this line appears consistently for several cycles:

```
No workspaces with eligible experiments found, consider disabling the job
```

### Disable

Set `EXPERIMENT_PROJECT_MIGRATION_ENABLED=false` using the same method above and apply. Wait for the completion signal to be stable before moving to Step 2.

## Step 2 — Datasets and prompts

Enable both once Step 1 is complete. They are independent of each other and can run in parallel.

<Tabs>
  <Tab title="Docker Compose">
    ```yaml wordWrap
    services:
      backend:
        environment:
          - DATASET_PROJECT_MIGRATION_ENABLED=true
          - PROMPT_PROJECT_MIGRATION_ENABLED=true
    ```
    ```bash wordWrap
    docker compose -f deployment/docker-compose/docker-compose.yaml \
      -f deployment/docker-compose/docker-compose.migration.yaml up -d backend
    ```
  </Tab>
  <Tab title="Kubernetes / Helm">
    ```yaml wordWrap
    component:
      backend:
        env:
          DATASET_PROJECT_MIGRATION_ENABLED: "true"
          PROMPT_PROJECT_MIGRATION_ENABLED: "true"
    ```
    ```bash wordWrap
    helm upgrade opik opik/opik -n opik -f values.yaml --version 2.2.17 --reuse-values
    ```
  </Tab>
</Tabs>

**Completion signals:**

```
No workspaces with eligible datasets found, consider disabling the job
No workspaces with orphan prompts found, consider disabling the job
```

Disable each flag individually once its completion signal is stable before moving to Step 3.

## Step 4 — Automation rules and alerts

These jobs inspect project references already stored in their own rows and have no dependency on the other jobs. Run them at any point — before, during, or after Steps 1–3.

    ```bash wordWrap

      -f deployment/docker-compose/docker-compose.migration.yaml up -d backend
    ```
  </Tab>
  <Tab title="Kubernetes / Helm">
    ```yaml wordWrap
    component:
      backend:
        env:

No workspaces with orphan alerts found, consider disabling the job
```

## Verifying the migration

Once all six jobs have reported their completion signals and been disabled, run these queries to confirm the result.

**ClickHouse — orphan experiments** (should be 0):

```sql wordWrap
SELECT countIf(project_id = '') AS orphan_experiments
FROM experiments FINAL;
```

**MySQL — orphan datasets** (should be 0):

```sql wordWrap
SELECT COUNT(*) FROM datasets WHERE project_id IS NULL OR project_id = '';
```

**MySQL — orphan prompts** (should be 0):

```sql wordWrap
SELECT COUNT(*) FROM prompts WHERE project_id IS NULL;
```

**ClickHouse — orphan optimizations** (should be 0):

```sql wordWrap
SELECT countIf(project_id = '') AS orphan_optimizations
FROM optimizations FINAL;
```

**MySQL — multi-project automation rules** (should be 0):

```sql wordWrap
SELECT COUNT(*) FROM (
  SELECT rule_id FROM automation_rule_projects
  GROUP BY workspace_id, rule_id HAVING COUNT(project_id) > 1
) t;
```

**MySQL — orphan alerts** (should be 0):

```sql wordWrap
SELECT COUNT(*) FROM alerts WHERE project_id IS NULL;
```

## Troubleshooting

| Symptom | Likely cause | Action |
|---------|-------------|--------|
| `Could not acquire lock` in logs | Normal on multi-replica deployments — only one replica runs per cycle | Harmless as long as `success` also appears each cycle |
| No progress after several cycles | Flag didn't propagate | Verify: Docker: `docker exec opik-backend-1 env \| grep MIGRATION` · Kubernetes: `kubectl exec deploy/opik-backend -n opik -- env \| grep MIGRATION` |
| Items landed in Default Project unexpectedly | A dependent job ran before its prerequisite finished | Use [`opik migrate`](/tracing/advanced/migrate-data) to relocate them |
| High MySQL or ClickHouse load during the run | Too many workspaces per cycle | Contact the Opik team — the batch size defaults are tunable |
| Sustained `error` results in job logs | Infrastructure or connectivity issue | Disable the job immediately, find the stack trace in the backend logs, resolve the underlying issue, then re-enable |
| No migration log lines at all, even with the flags set | `opik-backend` is on 2.2.18 or later, where the jobs no longer exist | Check the running version. Do not downgrade on your own, because 2.2.18 also changes the database schema: restore the snapshot you took before upgrading, or contact the Opik team |

## Upgrade to the latest release

Once every verification query returns 0:

1. Remove the six `*_PROJECT_MIGRATION_ENABLED` variables from your Helm values, or delete `docker-compose.migration.yaml` for Docker Compose. Opik 2.2.18 and later no longer read them.
2. Upgrade to the latest release as usual: `OPIK_VERSION=latest ./opik.sh` (after checking out the latest Opik repository) for Docker Compose, or the `helm upgrade` command from [Kubernetes deployment](/self-host/kubernetes) without `--version` for Helm.

## Next steps

Once migration is complete, update your SDK and pass `project_name` on your API calls. See [Upgrading to Opik 2.0](/opik-v2-upgrade) for the full code reference and examples.

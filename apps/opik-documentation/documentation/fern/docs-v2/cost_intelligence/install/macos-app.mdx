The macOS app is the rollout path for full coverage: it captures every Claude Code user on the machine, whether they work in the CLI or in the Code tab of the Claude desktop app. Developers keep working exactly as before — no base-URL change, no environment variables, nothing to install in the agent. The app sees the traffic anyway.

## How it works

Everything happens on the developer's machine. The app runs as a menu-bar app with a network extension, and macOS hands that extension the coding agent's traffic. The extension acts as a local MITM (man-in-the-middle): it terminates TLS on the device to read each call, then forwards it re-encrypted — with full certificate validation — to Anthropic or your LLM gateway, unchanged:

<Frame>
  <img src="/img/v2/cost-intelligence/macos-app-flow.svg" alt="macOS app data flow: an MDM delivers the app and its configuration profile to a managed Mac, macOS diverts Claude Code traffic to the app's network extension, calls are forwarded re-encrypted to the Anthropic API or a configured gateway, and metadata-only spans ship to Opik" />
</Frame>

The data landing in Opik is the same as the plugin produces. What differs is how the traffic gets seen:

| | Plugin (proxy) | macOS app (extension) |
| --- | --- | --- |
| How traffic arrives | Agent is pointed at a local port | The OS diverts the flows |
| Captures | Claude Code CLI | CLI **and** the Code tab of the Claude desktop app |
| Configuration touches | The agent's settings | Certificate trust only, set up by the app |
| Delivered via | MDM or Claude managed settings | MDM |
| TLS | Not intercepted | Terminated locally |
| Platforms | macOS, Linux, Windows | macOS only |

<Note>
  **The plugin is our recommended path.** It is simpler — no system extension,
  no certificate, no TLS interception — and it runs on macOS, Linux and
  Windows. Its limit is coverage: it captures the Claude Code **CLI**, not the
  Claude desktop app. Choose the macOS app when you want to roll Cost
  Intelligence out to all of your users, including the ones working in the
  Code tab of the Claude desktop app.
</Note>

### What is captured in the Claude desktop app

The Claude desktop app has three surfaces. The macOS app captures the one that runs Claude Code:

| Surface | Captured |
| --- | --- |
| **Code** tab | Yes, as Claude Code usage |
| **Chat** | No |
| **Cowork** | No |

Cost Intelligence reports Claude Code usage, so Chat and Cowork are out of scope and nothing from them is recorded.

<Note>
  Only connections opened after capture starts are recorded. If the Claude
  desktop app was already open when the macOS app was installed, quit and
  reopen it.
</Note>

## Deploy via MDM

Seven steps, delivered with the MDM you already run (Jamf, Kandji, Intune, JumpCloud). The order matters: the configuration profile goes out before the app, and the login-items profile after it.

Before you start, check that you have:

- **macOS 15 or later** on every target Mac. The app does not run on earlier versions.
- **Macs enrolled in your MDM**, with a current Apple push certificate. The profiles below are accepted only when an MDM pushes them, and with an expired push certificate they queue without ever reaching a Mac.
- **Access to your organization's AI Spend workspace** in Opik, to create the enrollment token.
- **The work email of each Mac's user.** A Mac enrolls under one person's email, and that is the name its spend is reported under.

<Steps>

### Create an enrollment token

In Opik, open your AI Spend workspace and go to **Enrollment tokens**, then select **Create token**. Copy the token right away: it starts with `opik_cipx_et_`, and that dialog is the only time it is shown in full.

One token serves the whole fleet. Each Mac spends it once to enroll and receives a credential of its own, which it keeps in the Keychain and renews by itself.

<Note>
  Create the token in the Opik deployment the Macs will send data to, and from
  the AI Spend workspace. A token from another deployment is not recognized,
  and the Macs it enrolls report into the workspace it was created in.
</Note>

### Push the configuration profile

Push the configuration profile to every target Mac, at device level. It does three jobs:

- It pre-approves the system extension, so activation is **silent**.
- It installs the proxy configuration, so the user is not asked to allow it.
- It forces the app's settings, so users can't change them in the app.

The example below is one file with all three payloads. Some MDMs take it as it is and others have you enter the payloads in separate forms; the per-MDM table in [Advanced](#advanced) says which. Either way, all three stay at device level.

Push it before the app is installed. An app that starts without the profile shows both approval prompts to the user.

### Install the app

Download `opik-cipx-v<version>.zip` from the [releases page](https://github.com/comet-ml/cost-intelligence-proxy/releases). It contains the notarized `Opik CIPX.app`, which embeds the extension and the capture engine, so there is nothing else to install.

Deliver the app to `/Applications` with your MDM's app deployment, or with a script that runs as root. The release is a zip archive and not an installer package, so if your MDM only accepts packages, wrap the app in one first. An example script is in [Advanced](#advanced) below.

The app does not update itself. To move the fleet to a newer release, deliver the new bundle the same way.

### Provision each Mac

Ship a file per user at `~/.opik-cipx-mac/config.toml`. It carries the two values a Mac needs to enroll, the token and the user's email:

```toml wordWrap
[opik]
base_url         = "https://www.comet.com/opik/api"
enrollment_token = "<enrollment token>"
user_email       = "<this user's work email>"

[capture]
capture_content = false
```

The token is the same on every Mac and the email is different on every Mac. If your MDM can substitute a per-user variable into a profile, you can deliver the email in a second, user-level profile and leave `user_email` out of the file. See *Setting each Mac's email* in [Advanced](#advanced).

The file lands in a user home. An MDM script running as root must find the logged-in user and write the file as that user, with the file at mode `0600` and the directory `0700`. Do not write it as root and change the owner afterwards: a root write into a directory the user controls follows a symlink placed there.

<Warning>
  Write the file before the app's first launch. The capture engine reads it
  only when it starts, so a file that arrives or changes later takes effect at
  the engine's next start. To apply a change right away, restart the engine:
  `sudo launchctl kickstart -k gui/<uid>/com.comet.opik-cipx.engine`, where
  `<uid>` is the user's numeric ID.
</Warning>

### Launch the app once

The app has to run once in the logged-in user's session. Any way of opening it works, including the user opening it themselves. To do it without involving the user, have the script that installed the app open it for them:

```bash wordWrap
launchctl asuser "$(id -u <username>)" open "/Applications/Opik CIPX.app"
```

From there the app handles everything itself: it activates the extension, starts capture, enrolls the Mac, and registers a login item so capture survives reboots. With the profile in place, the extension and the proxy configuration activate without a prompt. The user may be asked once to trust the app's certificate; see *Certificate trust* in [Advanced](#advanced).

### Lock capture on

The configuration profile fixes the capture setting inside the app, but a user can still switch the app's background item off in *System Settings → General → Login Items & Extensions*, which stops the capture engine. Push a second, separate profile that manages the app's login items. It greys out that switch and closes the remaining way to stop capture.

Push this one **after** the app is installed. If the profile reaches a Mac first, the switch is not locked.

### Verify

In Opik, open **Devices** in your AI Spend workspace. It lists every Mac that enrolled, with its user, its status, and when it last sent data:

- A Mac that is listed has enrolled.
- A recent time under **Last ingested** means that Mac's usage is arriving. A Mac nobody has used since it enrolled has nothing to send yet, so have its user run a prompt first.

This is the check that matters. The app is deliberately fail-open, so a Mac that is missing its token or its email looks completely healthy to its user and captures nothing.

<Accordion title="If a Mac is missing from the list">

On that Mac, check each step in turn:

```bash wordWrap
ls "/Library/Managed Preferences/com.comet.opik-cipx-app.plist"   # profile arrived
systemextensionsctl list | grep opik-cipx                         # extension activated
ls -l ~/.opik-cipx-mac/config.toml                                # token and email were delivered
```

The app also shows its enrollment state under *Settings → Account → This Device*.

## Advanced

<AccordionGroup>

<Accordion title="The configuration profile in detail">

The profile carries three payloads that do different jobs. All three are device-level. The system-extension and proxy payloads have no per-user form, so they must not be moved into a user-level profile.

**Pre-approving the system extension.** A `com.apple.system-extension-policy` payload allow-lists the capture extension so it activates silently: the developer never sees the *System Settings → General → Login Items & Extensions → Network Extensions* approval gate. This payload is accepted **only when the profile is pushed by an MDM the device is enrolled in**. Installing the profile by hand fails for the whole profile, so the forced settings don't land either. On a test machine without MDM, remove this payload and the proxy payload, install the rest, and approve the extension manually.

**Installing the proxy configuration.** Approving the extension is one consent gate, and saving the proxy configuration is a second: without help, every user sees *"Opik CIPX" Would Like to Add Proxy Configurations* the first time capture is enabled. A `com.apple.vpn.managed` payload of type `TransparentProxy` has the MDM install that configuration instead, and the app adopts it. `AuthenticationMethod` must be present: without it macOS rejects the whole profile.

**Forcing the app's settings.** A managed-preferences payload writes into the app's preference domain `com.comet.opik-cipx-app`. Forced values take precedence over anything the user sets, and the corresponding controls are disabled in the app's Settings window with a "Managed by your organization" note.

| Key | Type | Recommended | Why |
| --- | --- | --- | --- |
| `Cipx.isEnabled` | Boolean | `true` | Master capture switch; also drives automatic activation |
| `Settings.enableViewer` | Boolean | `false` | Local debug dashboard; no place in a fleet |
| `Settings.enableAdmin` | Boolean | `false` | Local control endpoint |
| `Settings.startAtLogin` | Boolean | `true` | Capture survives logout and reboot |
| `Settings.allowExtensionUninstall` | Boolean | `false` | Hides the uninstall action from users |
| `Settings.enabledHarnesses` | Array | `["com.anthropic.claude-code"]` | Which clients to capture, by code-signing ID |
| `Settings.engineEnvironment` | Dictionary | optional | Extra settings for the capture engine, as string values. See *Setting each Mac's email* and *Enrollment and credentials* below |

Validate the profile before pushing, because a malformed payload is silently ignored by some MDMs:

```bash wordWrap
plutil -lint opik-cipx-app.mobileconfig    # must print "OK"
```

On a Mac, read the forced values from the managed layer. Reading the app's own domain shows the user's values and makes a working profile look ignored:

```bash wordWrap
defaults read "/Library/Managed Preferences/com.comet.opik-cipx-app"
```

Where it goes in each MDM:

| MDM | Path |
| --- | --- |
| **Jamf Pro** | Two computer-level profiles. Settings: Configuration Profile → Application & Custom Settings → External Applications; domain `com.comet.opik-cipx-app`. System-extension and proxy payloads: a second computer-level profile. |
| **Kandji** | Library → Custom Profile → upload the `.mobileconfig` |
| **Intune** | Devices → macOS → Configuration profile → Preference file; domain `com.comet.opik-cipx-app` |
| **JumpCloud** | Custom macOS MDM Profile (Policy) → paste the `.mobileconfig`. Bind the policy to a device group. |

</Accordion>

<Accordion title="Enrollment and credentials">

The app does not use a shared API key. You distribute one **enrollment token**, and each Mac exchanges it, together with its user's email, for a credential of its own. That credential lives in the Mac's Keychain, is renewed by the app, and can read only what that Mac recorded.

A few consequences for running a fleet:

- **Rotation is a new token.** Creating a token does not invalidate the earlier ones, so Macs that are still waiting for the new value keep enrolling. Retire the old token on the **Enrollment tokens** page once the new one is everywhere.
- **Enrolled Macs are unaffected by rotation.** A Mac reads the enrollment token once. After that it uses and renews its own credential.
- **Removing a Mac.** The **Devices** page lists every enrolled Mac and lets you revoke one.

The token reaches the engine in one of two ways:

- **The per-user file** `~/.opik-cipx-mac/config.toml`, as in the steps above. The file is readable only by its user, which is why it is the recommended route.
- **The configuration profile**, as `OPIK_CIPX_ENROLLMENT_TOKEN` in `Settings.engineEnvironment`. This needs no script, but a profile is not a secret store: it lands in `/Library/Managed Preferences/`, which every local user can read. A value in the profile takes precedence over the file.

The Opik address works the same way: `base_url` in the file, or `OPIK_CIPX_BASE_URL` in `Settings.engineEnvironment`.

</Accordion>

<Accordion title="Setting each Mac's email">

Enrollment needs the email of the person using the Mac. It is the one value in this setup that differs from Mac to Mac, and a configuration profile is a static file: macOS substitutes nothing into it at install time. Pick the route your MDM supports:

- **Your MDM substitutes per-user variables** (Jamf Pro `$EMAIL`, Kandji `$EMAIL`, Intune `{{mail}}`). Leave the main profile as it is and deliver the email in a second, small profile. Its managed-preferences payload for `com.comet.opik-cipx-app` forces this one key:

  ```xml wordWrap
  <key>Settings.engineEnvironment</key>
  <dict>
    <key>OPIK_CIPX_USER_EMAIL</key>
    <string>$EMAIL</string>
  </dict>
  ```

  Assign this profile so that the variable resolves to the Mac's user. In Jamf Pro that means setting the profile's level to User. Give it its own `PayloadIdentifier` and `PayloadUUID`.

  macOS combines the two profiles key by key, and `Settings.engineEnvironment` is one key. If you set other engine values in a profile, such as `OPIK_CIPX_BASE_URL`, put them in this same dictionary and not in the main profile.

  Check one Mac before rolling out: the app's *Settings → Account* shows the address it received. If the variable was not substituted, the Mac receives the variable's name as text, the app rejects it as an address, and the Mac does not enroll.

- **Your MDM delivers device-level profiles only** (JumpCloud). Write `user_email` into each Mac's `config.toml` from the provisioning script. The script needs a way to know whose Mac it is running on, for example a lookup table from the MDM's device ID to the user's email.

Do not put one literal address in a profile that goes to many Macs. Every Mac would then enroll as that one person.

The app checks the address before enrolling. With a missing or malformed one the Mac does not enroll, and *Settings → Account → This Device* reports it as not configured.

</Accordion>

<Accordion title="Example install script">

A script for MDMs that run scripts as root. It waits for the configuration profile, installs the app if it is missing, writes the per-user file if it is missing, and opens the app for the logged-in user. It is safe to run repeatedly. Keep the enrollment token out of the saved script. Store the script without real values, have your MDM supply them when it runs, and do not print them in the script's output. Anyone who has the token can enroll a device into your workspace, so a filled-in copy in a repository or a ticket is a leaked credential.

How the values arrive depends on the MDM:

- **The MDM substitutes variables into the script text** (JumpCloud command variables). Put the variable where the placeholder is.
- **The MDM passes parameters as arguments** (Jamf Pro, where the first free parameter is `$4`). Nothing is substituted into the script text, so replace the placeholder line with `TOKEN="${4:-}"`. A script parameter is the same for every Mac the policy covers, so set `EMAIL=""` and deliver the email with the user-level profile from *Setting each Mac's email*.

```bash title="install-opik-cipx.sh" wordWrap
#!/bin/bash
# Run as root. Installs Opik CIPX for the user logged in at the console.
set -u
export LC_ALL=C
VERSION="<release version, for example 0.0.91>"
# Supplied by your MDM when the script runs. Never save real values here.
TOKEN="<enrollment token variable>"
# This Mac's user. Leave empty when a profile delivers the email instead.
EMAIL="<user email variable>"
APP="/Applications/Opik CIPX.app"

# Accept only a plain token and a plain address. This stops a placeholder the MDM
# did not fill in, and any value that would break out of the TOML strings below.
case "$TOKEN" in opik_cipx_et_?*) ;; *) echo "enrollment token missing or not substituted"; exit 1;; esac
case "$TOKEN" in *[!A-Za-z0-9_-]*) echo "unexpected character in the enrollment token"; exit 1;; esac
if [ -n "$EMAIL" ]; then
  case "$EMAIL" in *[!A-Za-z0-9._%+@-]*|*@*@*) echo "unexpected character in the email"; exit 1;; esac
  case "$EMAIL" in ?*@?*.?*) ;; *) echo "email not substituted, or not an address"; exit 1;; esac
fi

CONSOLE_USER="$(/usr/bin/stat -f%Su /dev/console)"
case "$CONSOLE_USER" in root|_mbsetupuser|"") echo "no user logged in"; exit 0;; esac
USER_ID="$(/usr/bin/id -u "$CONSOLE_USER")"
USER_HOME="$(/usr/bin/dscl . -read "/Users/$CONSOLE_USER" NFSHomeDirectory | /usr/bin/awk '{print $2}')"

# Without the profile, the first launch would prompt the user.
[ -f "/Library/Managed Preferences/com.comet.opik-cipx-app.plist" ] || { echo "profile not installed yet"; exit 0; }

CHANGED=no

# Install the app, unless something else already delivered it.
if [ ! -d "$APP" ]; then
  WORK="$(/usr/bin/mktemp -d)"; trap '/bin/rm -rf "$WORK"' EXIT
  /usr/bin/curl -fsSL --retry 3 -o "$WORK/app.zip" \
    "https://github.com/comet-ml/cost-intelligence-proxy/releases/download/v${VERSION}/opik-cipx-v${VERSION}.zip" || exit 1
  /usr/bin/ditto -x -k "$WORK/app.zip" "$WORK/app"
  /usr/sbin/spctl -a -t exec "$WORK/app/Opik CIPX.app" || { echo "notarization check failed"; exit 1; }

  /usr/bin/ditto "$WORK/app/Opik CIPX.app" "$APP"
  /usr/sbin/chown -R root:wheel "$APP"
  /usr/bin/xattr -dr com.apple.quarantine "$APP" 2>/dev/null || true
  CHANGED=yes
fi

# Provision this user, also when the app was already there. The file is written
# as the user and never as root: a root write into a directory the user controls
# would follow a symlink placed there.
CONFIG_DIR="$USER_HOME/.opik-cipx-mac"
if [ ! -f "$CONFIG_DIR/config.toml" ]; then
  {
    echo '[opik]'
    echo 'base_url         = "https://www.comet.com/opik/api"'
    echo "enrollment_token = \"$TOKEN\""
    [ -n "$EMAIL" ] && echo "user_email       = \"$EMAIL\""
    echo
    echo '[capture]'
    echo 'capture_content = false'
  } | /usr/bin/sudo -u "$CONSOLE_USER" /bin/sh -c \
      'umask 077; /bin/mkdir -p "$1" && /bin/cat > "$1/config.toml"' sh "$CONFIG_DIR" \
    || { echo "could not write config.toml"; exit 1; }
  CHANGED=yes
fi

[ "$CHANGED" = yes ] || { echo "nothing to do"; exit 0; }

# The engine reads the file only when it starts, so restart it if it is running.
/bin/launchctl kickstart -k "gui/$USER_ID/com.comet.opik-cipx.engine" 2>/dev/null || true
/bin/launchctl asuser "$USER_ID" /usr/bin/open "$APP"
```

Run it on a schedule or at check-in instead of once: a Mac that was offline, had nobody logged in, or had not received the profile yet is picked up on a later run. So is a second person who logs in to a Mac that already has the app, and a Mac where your MDM installed the app by other means.

To update an installed Mac, quit the app, replace the bundle the same way, restart the engine and open the app again.

</Accordion>

<Accordion title="Activation and first launch">

On first launch the app activates the system extension, starts the capture engine, enables the proxy configuration, and registers a login item so capture returns after every reboot. The engine also applies your org's [cost policies](/cost-intelligence/roll-out-cost-policies) to the machine automatically.

Activation is fail-safe: any error in the chain turns capture back off rather than leaving a half-configured proxy.

Ways to trigger the first launch, in order of preference:

1. A package postinstall script that opens the app in the logged-in user's session.
2. A LaunchAgent shipped alongside the app. This also covers users who weren't logged in at install time.
3. An MDM "run as current user" script.

</Accordion>

<Accordion title="The data path in detail">

The four numbered steps in the diagram, in full:

1. **The developer works as usual.** They prompt Claude Code from the CLI or the Code tab of the Claude desktop app. Neither is configured, pointed at a proxy, or aware the app exists.
2. **macOS diverts the agent's API calls to the app.** The system extension terminates TLS on the device so the app can read each call and attribute its cost — that interception happens on the device only, and it never leaves the machine.
3. **The call is forwarded unchanged.** The app opens its own TLS connection — to the Anthropic API by default, or to your LLM gateway when one is configured — with full certificate validation, and passes the request and response through untouched.
4. **Metadata ships to Opik on the side.** Counts, costs, and structure — [never content](/cost-intelligence/data-privacy-security) — go to your Opik workspace asynchronously. This side path never sits between the developer and the model: if anything in it fails, the agent keeps working.

</Accordion>

<Accordion title="Certificate trust">

To categorize traffic rather than just count bytes, the extension terminates TLS locally, which means the client must trust the interception certificate.

By default the certificate authority is minted **per device**, with a private key that is hardware-backed and non-extractable. This is deliberate: there is no shared fleet-wide interception key, so compromising one device does not compromise the fleet. Trust is established on the device that generated it, and the user confirms it once with their login password or Touch ID.

For a rollout with no prompt at all, the app can instead sign under a certificate chain your organization owns: a root certificate that you generate once and push to every Mac with your MDM's certificate payload, and a signing certificate issued from it that is delivered alongside the app. A Mac that has both uses your chain. A Mac that doesn't falls back to its own per-device authority, so nothing is blocked while this is being set up. Email [sales@comet.com](mailto:sales@comet.com) to set this up.

In both cases the certificate authority carries constraints limiting it to the specific model-provider hostnames, so even a fully trusted authority cannot vouch for any other domain. That is worth raising early in a security review, because it's the property that makes local termination defensible.

</Accordion>

<Accordion title="Uninstall">

```bash wordWrap
# Remove both profiles (settings and login items) via your MDM, or:
sudo profiles remove -identifier com.comet.opik-cipx-app.managed

# Tear down cleanly, then remove the app
open -a "/Applications/Opik CIPX.app" --args disable
sudo rm -rf "/Applications/Opik CIPX.app"

# Local state, including the per-device certificate
rm -rf ~/.opik-cipx-mac ~/Library/Application\ Support/opik-cipx
```

Removing the app without disabling first leaves an orphaned system-extension registration, so prefer the `disable` step.

Then revoke the Mac on the **Devices** page of your AI Spend workspace, so its credential can no longer be used.

</Accordion>

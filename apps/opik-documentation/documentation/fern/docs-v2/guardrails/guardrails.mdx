A **rule** is one check, configured. This page covers the three rule types Opik offers: what each one detects, what you configure on it, and what it needs in order to run.

You put PII, Topic, and prompt injection rules into a [policy](/guardrails/policies) in the Opik UI, and your application runs that policy by name. Configuration lives in Opik; your code only calls `validate`.

## Quickstart

Create a policy in the UI with the rules you want, then build a guardrail from it and validate your text. A failing check raises, so the protected path only continues when `validate` returns.

```python wordWrap
from opik.guardrails import Guardrail
from opik import exceptions

guardrail = Guardrail.from_stored_policies(names=["no-financial-advice"])

llm_response = "You should buy some NVIDIA stocks!"

try:
    guardrail.validate(llm_response)
except exceptions.GuardrailValidationFailed as e:
    print(e)
```

The call is blocking, since the whole point is to stop your application before it returns a response you would not want a user to see.

<Tip>
  See [Policies](/guardrails/policies) for creating a policy, combining several of them, and enforcing one across
  every application in the workspace.
</Tip>

<Note>
  Rules, and the policies that hold them, are checked by Opik itself and are available on the Enterprise plan of
  Opik Cloud.
</Note>

## The three rule types

Providers like OpenAI or Anthropic already block the most universal risks, such as harmful or malicious content. Opik's rules cover the residual risks, which tend to be specific to your product and need configuring in more detail.

Each rule asks a small language model focused questions, which keeps a check fast enough to run inline on every request.

Rules are configured in a policy: switch the rule on and fill in its fields. They can also be [defined in code](#defining-rules-in-code).

### PII

Detects sensitive personal information such as names, addresses, email addresses, phone numbers, and credit card details.

**What you configure**

- **Personal data to block** — which categories to look for: credit card numbers, phone numbers, email addresses, bank account numbers (IBAN), IP addresses, vehicle registration plates, postal addresses, person names, cryptocurrency wallet addresses, medical license numbers, and URLs.

_Each category is one yes-or-no question to a small language model._

### Topic

Keeps inputs and outputs on topic.

**What you configure**

- **Restricted topics** — text must not be about any of these.
- **Allowed topics** — text must be about at least one of these.

You can set either list or both, but a topic cannot be in both. Restricted topics are the common case: name what your application must stay away from.

_A small language model picks the topic the text is about from each list._

### Prompt injection

Detects attempts to make your LLM ignore, override, or reveal its instructions, along with other malicious queries. Use it on user inputs to block jailbreaks and injection attacks before they reach your model.

There is nothing to configure: switch the rule on.

_This guardrail relies on a small language model._

## Handling a failure

A failing guardrail raises an exception, and your application code needs to handle it — retry, fall back to a safe default, or return an error, whichever suits the situation.

<Warning>
  Guardrails fail closed. If a check cannot be evaluated (for example Opik is unreachable, the request times out,
  or guardrails are not available in the workspace),
  `validate` raises `opik.exceptions.GuardrailValidationError` rather than letting the text through. This exception subclasses `GuardrailValidationFailed`, so an existing
  `except GuardrailValidationFailed` block also stops the request. Structure your code so the protected path only
  proceeds when `validate` returns successfully.
</Warning>

### Streaming responses and long inputs

Call `guardrail.validate` repeatedly to check a response chunk by chunk, or to check parts of a long input separately. The results are added as additional spans on the same trace.

```python wordWrap
for chunk in response:
    try:
        guardrail.validate(chunk)
    except exceptions.GuardrailValidationFailed as e:
        print(e)
```

## Working with the results

When a guardrail fails on an LLM call, Opik adds the information to the trace automatically. You can filter the traces in your project down to those that failed a guardrail.

## Limits

- A Topic rule takes up to 254 topics in each list, each up to 256 characters.
- A guardrail checks at most 32 PII, Topic, and prompt injection rules, counting those it takes from policies.
- Together those rules can ask the model at most 64 questions: one for each PII class, one for each topic list, and one for prompt injection. A guardrail that needs more is rejected before any check runs.

## Defining rules in code

Rules can also be listed inline instead of stored in a policy. This is handy for a quick experiment or a check that only one script cares about.

<Warning>
  Rules defined this way are invisible to everyone else and can only be changed by editing and redeploying your
  application. Prefer a [policy](/guardrails/policies) for anything that runs in production.
</Warning>

```python wordWrap
from opik.guardrails import Guardrail, PII, Topic
from opik import exceptions

guardrail = Guardrail(
    rules=[
        Topic(restricted_topics=["finance", "health"]),
        PII(entities=["CREDIT_CARD", "PERSON"]),
    ]
)

try:
    guardrail.validate("You should buy some NVIDIA stocks!")
except exceptions.GuardrailValidationFailed as e:
    print(e)
```

Each rule type has a matching class, taking the same settings the UI exposes:

| Rule | Class | Arguments |
| --- | --- | --- |
| PII | `PII` | `entities` (any of `CREDIT_CARD`, `PHONE_NUMBER`, `EMAIL_ADDRESS`, `IBAN_CODE`, `IP_ADDRESS`, `NRP`, `LOCATION`, `PERSON`, `CRYPTO`, `MEDICAL_LICENSE`, `URL`) |
| Topic | `Topic` | `restricted_topics`, `allowed_topics` |
| Prompt injection | `PromptInjection` | none |

### Upgrading from guards

Earlier SDK versions called rules _guards_ and ran PII, Topic, and prompt injection on the guardrails server with a threshold you set. Opik now checks them itself and sets the thresholds, so code written for the older API needs these changes:

| Before | Now |
| --- | --- |
| `Guardrail(guards=[...])` | `Guardrail(rules=[...])` |
| `from opik.guardrails.guards import ...` | `from opik.guardrails import ...`, or `opik.guardrails.rules` |
| `PII(blocked_entities=[...], threshold=..., language=...)` | `PII(entities=[...])` |
| `Topic(restricted_topics=[...], allowed_topics=[...], threshold=...)` | `Topic(restricted_topics=[...], allowed_topics=[...])` |
| `PromptInjection(threshold=...)` | `PromptInjection()` |

`LLMJudge`, `CustomGuardrail`, and `create_custom_guardrail` are no longer part of the SDK. `Guardrail.from_stored_policies(names=[...])` is unchanged.

## Manual guardrails

For a check that fits none of the rule types — a one-off heuristic, or a business rule that is genuinely just code — you can run it yourself and log the result to Opik directly. No rule class is involved.

<AccordionGroup>
  <Accordion title="Example: blocking competitor mentions">
    ```python wordWrap
    import opik
    import opik.opik_context
    import traceback

    # Brand mention detection
    competitor_brands = [
        "OpenAI",
        "Anthropic",
        "Google AI",
        "Microsoft Copilot",
        "Amazon Bedrock",
        "Hugging Face",
        "Mistral AI",
        "Meta AI",
    ]

    opik_client = opik.Opik()


    def check_competitor_mentions(generation: str, trace_id: str) -> str:
        # Start the guardrail span first so the duration is accurately captured
        guardrail_span = opik_client.span(name="Guardrail", input={"generation": generation}, type="guardrail", trace_id=trace_id)

        # Manual guardrail logic - detect competitor brand mentions
        found_brands = []
        for brand in competitor_brands:
            if brand.lower() in generation.lower():
                found_brands.append(brand)

        # The key `guardrail_result` is required by Opik guardrails and must be either "passed" or "failed"
        if found_brands:
            guardrail_result = "failed"
            output = {"guardrail_result": guardrail_result, "found_brands": found_brands}
        else:
            guardrail_result = "passed"
            output = {"guardrail_result": guardrail_result}

        # Log the spans
        guardrail_span.end(output=output)

        # Upload the guardrail data for project-level metrics
        guardrail_data = {
            "project_name": opik_client._project_name,
            "entity_id": trace_id,
            "secondary_id": guardrail_span.id,
            "name": "TOPIC", # Supports either "TOPIC" or "PII"
            "result": guardrail_result,
            "config": {"blocked_brands": competitor_brands},
            "details": output,
        }
        try:
            opik_client.rest_client.guardrails.create_guardrails(guardrails=[guardrail_data])
        except Exception as e:
            traceback.print_exc()

        return generation


    @opik.track
    def main():
        good_generation = "You should use our AI platform for your machine learning projects!"
        check_competitor_mentions(good_generation, opik.opik_context.get_current_trace_data().id)

        bad_generation = "You might want to try OpenAI or Google AI for your project instead."
        check_competitor_mentions(bad_generation, opik.opik_context.get_current_trace_data().id)


    if __name__ == "__main__":
        main()
    ```
  </Accordion>
</AccordionGroup>

The guardrail spans appear alongside your traces just like the built-in rules, showing what was detected and whether the check passed or failed.
